# デバイスの仕様

純正ドライバー `pxmb86m0x_usb.sys` (v1.6.0.0) の解析, 第三者から提供された解析, 実機での確認による。
PIX-DT195W は、純正の Mac 用ドライバー (StationTV for Mac 1.6.1 の `DT195Lib`) と Windows 用ドライバー (v1.3.2.12) の解析、実機での確認による (下の "PIX-DT195W" セクション)。
確度は見出しなどに [確] (確定) と [推] (推定) で示す。
実装との対応は [development.md](development.md) の "構成" セクション。

## ハードウェア

| 項目 | 内容 |
|---|---|
| 製品 | PIXELA PIX-DT295。USB 接続の地上, BS, 110度CS デジタルチューナー |
| USB ID | VID 0x06B8 (PIXELA) / PID 0x103B (兄弟機: 0x103C PIX-DT295W, 0x103A PIX-DT195, 0x1040 PIX-DT195W, 0x1046 XIT-BRK100W (Xit Brick)) |
| USB | USB 2.0 High-Speed, bcdDevice 0x0100, バスパワー (MaxPower 500 mA) |
| ブリッジ / SoC | Fujitsu MB86M03A。USB ブリッジ兼 H.264 トランスコーダーで、ファームウェアは毎回ホストからロード。純正ドライバーとファームウェアの名前に合わせて、以下とコードでは MB86M01 と表記 |
| B-CAS | 本体に内蔵 (ドライバーの設定 BCASNUM=1) |

フロントエンド (フロントエンド種別 3。下の "兄弟機" セクション) [確。型番は基板の刻印]:

| 役割 | チップ | I2C (8bit / 7bit) | アクセス |
|---|---|---|---|
| ISDB-T 復調 | Toshiba TC90532XBG (TC90522 系) | 0x20 / 0x10 | 直接 |
| ISDB-S 復調 | 同じチップの S 側 | 0x22 / 0x11 | 直接 |
| ISDB-T チューナー | MaxLinear MxL661 (純正ドライバーでは MxL603) | 0xC0 / 0x60 | T 復調のゲートウェイ経由 |
| ISDB-S チューナー | Sony CXD2832A (HORUS3A) | 0xC0 / 0x60 | S 復調のゲートウェイ経由 |

- ドライバー内の Sony `sut_pj785_*` (CXD2858ER) はフロントエンド種別 5 用で、DT295 では未使用
- TS バスは 1 本で、同時に流せるのは片方の復調のみ。
  T 復調 reg 0x0E の bit 2-0 が 001 で T の TS をバスに流し、111 でバスを放す (純正の選局列は地デジで 0x71、衛星で 0x77)。
  S 側は reg 0x07 が 0x33 のままだとロックしても TS が出ず、reg 0x1C の bit 7 と reg 0x1F の bit 5, 4, 1, 0 が 0 のときのみ出力する (第三者が実機で確認)
- 2 つのチューナーが同じ 0xC0 なのは、それぞれ別の復調チップのゲートウェイの先にあるため
- クロック: MxL661 は 16 MHz の水晶 (基板の X1) で、clock-out は有効。
  HORUS3A は外部基準 16 MHz で、横の水晶の場所 (X2) が空いているので、MxL661 の clock-out を受けていると見られる。
- LNB 給電: DT295 のドライバーは制御しない (board vtable の slot 18/19 が STATUS_NOT_SUPPORTED。DT410 のみ GPIO3 で制御する)。
  製品の仕様も BS / CS アンテナへの電源供給には対応していない。

## 兄弟機 (PIX-DT295W、PIX-DT195、XIT-BRK100W)

純正ドライバーの静的解析による (どの機種も実機では確認していない):

- 機種の種別は VID / PID で決まる (`dev_DetectBoardType`)。
  VID 0x06B8 で、PID 0x103A (PIX-DT195) と 0x103B (DT295) が 7, 0x103C (PIX-DT295W) と 0x1046 (XIT-BRK100W) が 8, 0x1039 / 0x1043 が 5, 0x1038 が 6, ほかは 10。
  第三者から提供された解析の「ボード種別 7」はこの値。
- PIX-DT195 (PID 0x103A) は Mac 用の 1 チューナー機で、Windows の純正ドライバーは DT295 と区別しない (同じ種別 7)。
  Mac 用ドライバー (StationTV for Mac の `DT195Lib`) も、同じチップ (TC90522 系の復調の 1 組 (ドライバーのクラス名は `TC90522XBG`)、MxL661、HORUS3A) を同じ I2C のアドレスと同じ手順で動かし、MxL661 の初期化の表は Windows 用とバイト単位で同じ。
  本ドライバーは PIX-DT195 を PIX-DT295 と同じ処理で、PIX-DT295W を PIX-DT195W と同じ処理で動かす (PIX-DT295W と PIX-DT195W は基板が同じ。下の "基板" セクション)
- DT295W と XIT-BRK100W は同じ種別 8 で、ボードのオブジェクトもフロントエンドの作り方も同じ。
  INF のハードウェア設定 (水晶の負荷容量 9 / 25) も同じものを使う。
  違うのは、INF が XIT-BRK100W には TS の出力として System1 のみを登録すること (DT295 と DT295W は System1 と System2)。
- フロントエンド: 種別 7 (DT295) はフロントエンド種別 3 を 1 つ作る (チューナー 1 つ。復調 0x20 / 0x22, MxL603 の水晶の負荷容量は `XTAL_CAP_SYSTEM1`, 既定 9)。
  種別 8 はフロントエンド種別 1 を 2 つ作る: 1 つ目は復調 0x20 / 0x22 (負荷容量 `CapacitanceOfSystem1`), 2 つ目は 0x24 / 0x26 (`CapacitanceOfSystem2`)。
  つまりチューナーが 2 つある。
- どちらのフロントエンドも、チップの組み合わせ (TC90522 系の復調の T と S、MxL603、HORUS3A) と、復調の処理、電源投入時の初期化は DT295 と同じ内容。
  種別 8 の 2 つ目のチューナーのみ、初期化の後に処理が 1 つ追加される (内容は未解析)。
- 種別 8 の LSI は 1 つで、1 つ目のチューナーの TS は System1 (EP 0x81)、2 つ目は System2 (EP 0x86) を通る (v1.3.2.12 の解析。PIX-DT195W の実機でも同じ。下の "PIX-DT195W" セクション)。
  2 つ目の LSI (bRequest 0xBD) への読み書きは、LSI 0 の reg 0x0801F0 の bit 0x2000 が立っているときのみ行う (機種ではなくハードウェアで判断している)。

## PIX-DT195W

Mac 用の 2 チューナー機 (PID 0x1040)。
Windows の純正ドライバーの種別の判定では 10 (未対応) で、同じ構成の PIX-DT295W (種別 8) の処理と、Mac 用ドライバーの処理を参考にした。
実機で確認したこと [確]:

- USB の記述子とエンドポイントは PIX-DT295 と同じ。
  製品の文字列は `PIX-DT195W`
- Windows 用のファームウェア (`mb86m01_assp_osec_idle.bin`, `trc_m_h.bin`) でも、Mac 用のソフトに入っている同じ名前のファームウェア (PIX-DT195 用のビルド) でも、起動と認証ができ、System1 と System2 で受信できる。
  2 つの違いと、受信した TS の比較は下の "Mac 用のファームウェア" セクション。
- 復調は TC90522 で、ISDB-T と ISDB-S の組が 2 つある (0x20 / 0x22 と 0x24 / 0x26)。
  チューナー (MxL661 と HORUS3A) は組ごとにあり、どれも 0xC0 でその組のゲートウェイの先にある。
- 復調の TS の出力は 2 本 (A と B)。
  A はブリッジの System1 の入力と raw-TS の取り込みに、B は System2 の入力につながる。

### 基板

PIX-DT195W と PIX-DT295W の基板の写真による [確: 刻印]:

- 2 つは同じ基板 (シルクの型番 `TVB7700Rev.A`) で、部品の配置も同じ。
  製品のラベルは PIX-DT195W が `TVB7700MC Rev.01`、PIX-DT295W が `TVB7700PX Rev.01`
- ブリッジは Fujitsu MB86M03A (IC200)
- 復調は Toshiba TC90522XBG が 1 個 (IC100)。
  ISDB-T と ISDB-S の復調を 2 組ずつ持つチップで、I2C の 0x20 / 0x22 と 0x24 / 0x26 はこの 1 個の 2 組
- チューナーは MaxLinear MxL661 と Sony CXD2832A (刻印は `D2832A`) が 2 個ずつ
- 前段の水晶は MxL661 の横の X1 の 1 つだけで、復調の水晶の場所 (X100) は空いている (2 つ目の MxL661 が 1 つ目のクロック出力で動くことと合う)

### TS の出力先

TC90522 の TS の出力は 4 本 (P0-P3) で、どの組の TS をどの出力に出すかは、1 つ目の組 (T0 = 0x20, S0 = 0x22) のレジスターの 3 ビットずつの欄で選ぶ。
値は組の番号で、1 が 1 つ目、3 が 2 つ目、7 は出さない。
同じ出力に ISDB-T と ISDB-S の両方の組を指定すると、ISDB-T の TS が出る。

| 出力 | ISDB-T の欄 | ISDB-S の欄 | PIX-DT195W での行き先 |
|---|---|---|---|
| P0 (出力 A) | T0 reg 0x0E bit 2-0 | S0 reg 0x07 bit 2-0 | ブリッジの System1 の入力と 1 つ目の取り込み |
| P1 | T0 reg 0x0E bit 6-4 | S0 reg 0x07 bit 6-4 | ブリッジに届かない (純正は電源投入時に T を 7、S を 1 にする) |
| P2 (出力 B) | T0 reg 0x0F bit 6-4 | S0 reg 0x08 bit 6-4 | ブリッジの System2 の入力と 2 つ目の取り込み |
| P3 | T0 reg 0x0F bit 2-0 | S0 reg 0x08 bit 2-0 | ブリッジに届かない |

- 4 本の欄の割り当ては、TC90522 の 4 つの復調を 4 本でブリッジに入れる 2T2S の機種 (PLEX PX-W3U4) の設定値 (T0 reg 0x0E = 0x77, 0x0F = 0x13, S0 reg 0x07 = 0x31, 0x08 = 0x77。px4_drv) と合う [推: レジスターの意味は公開されていない]
- PIX-DT195W で P1 か P3 にだけ出した ISDB-T の TS は、どちらの取り込みにも届かなかった。
  ブリッジの端子のレジスター (0xF10124, 0xF10128, 0xF1012C) のビットを 1 つずつ変えても同じ [確]。
  ブリッジ (MB86M03A) の TS の入力も、同じ作りのストリームのユニット 2 つ (0x0190 の帯と 0x00D0 の帯。どちらも入力、リングのエンジン、DMA、暗号を持つ) の入力 (0x01901000 と 0x00D21000) のみで、純正のファームウェア (Windows 用と Mac 用の idle と trc_m_h) のどのユニットも、この 2 つのほかに TS の入力を設定しない [推: ファームウェアのコードから数えた]。
  そのため、PIX-DT195W が同時に流せるのは、ハードウェアとしても 4 つの復調 (2T2S) のうち 2 つ (2TS)
- 衛星の選局は、その出力の T を 7 (0x77) にしてから S を書く
- ISDB-T の値は実機で確認した: T0 reg 0x0E = 0x33 で 2 つ目の組の TS が出力 A に出る (0x31, 0x30 では出ない)。
  0x0F = 0x30 (純正の 2 チューナー機の値) で出力 B に出る。
- ISDB-S は純正ドライバーの解析のみ [推] (BS / CS のアンテナで確認していない)
- PIX-DT295 の復調 (TC90532) は組が 1 つで、選局のたびに両方の出力を同じ組にする (0x0E = 0x71, 0x0F = 0x10。衛星は 0x07 = 0x11, 0x08 = 0x10)

### 初期化

純正の 2 チューナー機の処理 (PIX-DT295 の列からの違い) [確: 純正ドライバー。2 つ目の組の 0x1C の意味は不明]:

- 1 つ目の組: T の初期化表に 0x04 = 0x02 を加え、S は 0x07 = 0x11, 0x1D = 0xBA, 0x1E = 0x30
- 2 つ目の組: S の 0x07 / 0x08 は書かない (2 つ目の組では TS の出力先のレジスターではない)。
  初期化の後に、T reg 0x1C の bit 5-4 を 11 にする。
- MxL661: 1 つ目は reg 0x01 = 0x89 (水晶の負荷容量 9 pF、クロック出力あり)。
  2 つ目は 0x01 = 0x99 (25 pF), 0x02 = 0x40, 0x6D = 0x80 で、1 つ目のクロック出力で動く (MxLWare の水晶の共有)。
  そのため 2 つ目は 1 つ目の後に初期化する。
  実機では、この値で両方の C/N が 38-40 dB になる (PIX-DT295 の値のままだと 33 dB 前後で、2 つ目を初期化すると 1 つ目が 23-28 dB に下がる)。
- S の GPIO (S 側の待機で bit 5-4 を 11、復帰で 10): 1 つ目は S0 reg 0x1E, 2 つ目は S0 reg 0x1D
- 電源投入時に T0 reg 0x0E の bit 6-4 を 7、S0 reg 0x07 の bit 6-4 を 1 にする

### 2 つのストリーム

1 つ目のチューナーは出力 A から System1 (EP 0x81)、2 つ目は出力 B から System2 (EP 0x86) で、同時に流せる (下の "TS ストリーム (System2 / EP 0x86)" セクション)。
片方を止めて開始し直しても (System1 の trc ファームウェアのホットロードを含む)、もう一方は途切れない (実機)。
raw-TS では、出力 A を 1 つ目の取り込み、出力 B を 2 つ目の取り込みで受け、同時に流せる (下の "raw-TS 経路で使うブロック" セクション)。

### Mac 用のファームウェア

StationTV for Mac 1.6.1 と Xit for Mac の `DT195Lib.framework/Versions/A/Resources/` にある `mb86m01_assp_osec_idle.bin`, `trc_h_h.bin`, `trc_m_h.bin` は、PIX-DT195 用のビルド (ビルドの日付は 2015-09-17。Windows 用は 2015-03-05)。
ファイルの形式は Windows 用と同じで、Windows 用と比べると次のとおり [確]:

- idle: 違うのはビルドの印のみで、System2 と認証の処理は同じ
- trc_m_h: TS の多重化のプログラム (2 つのユニットに同じものを載せる) が全体に手直しされている (152 関数が 155 関数)。
  ほかに、TS の DMA を設定する別のユニットの 1 関数が違う。
  認証の処理、ARM のコード、エンコーダーは同じ

trc_m_h で処理が変わったのは次の 3 か所で、ほかは書き方の違い (関数の分け方など) だった [確: 処理の違い / 推: 直した理由]。
どれも ECM やデスクランブルには関わらない。

- PCR: PMT の PCR_PID が 1 つ目のストリーム (映像) の PID と同じ番組で、多重化が PCR を作り直すときの連続性カウンターの扱い。
  Windows 用は同じ PID に PCR 用のカウンターを混ぜることがあり、Mac 用はそれを避ける
- PMT: 番組の PMT の版 (version_number) が変わったときの処理で、内部の値を 1 つ書き足す
- TS の DMA: 16 単位未満の短い転送の設定の値 (長い転送と同じ値にした)

raw-TS モードはファームウェアを使わないので、どの違いも通常モードのみに関わる。

同じ個体を Mac 用と Windows 用で順に起動して比べた (PIX-DT195W は地上波、PIX-DT295 は 110 度 CS) [確]:

- どちらも認証が通り、System1 (全サービスと 1 サービス) で受信できる。
  PIX-DT195W は System2 でも受信できる
- TS の欠けと TEI は無く、スクランブルが解けていないパケットも無い
- PID の構成と量の比率、System1 の開始までの時間も同じ
- CS では、PCR を映像の PID に載せている番組 (ND06 の 8 番組と ND16 の 4 番組) でも、映像の PID に PCR だけのパケットが混ざる番組 (ND08) でも、連続性カウンターの飛びは無い (全サービスと 1 サービス)。
  上の PCR の違いが表に出る放送は、見つからなかった
- BS は確認していない

## レジスターアクセス (ベンダーリクエスト 0xBC) [確]

MB86M01 のレジスター空間を 16bit のワード単位で読み書きする。
データはビッグエンディアン。

| 操作 | bmRequestType | bRequest | wValue | wIndex | データ |
|---|---|---|---|---|---|
| 16bit 読み | 0xC0 | 0xBC | (addr>>16)<<8 | addr&0xFFFF | 2 B |
| 16bit 書き | 0x40 | 0xBC | (addr>>16)<<8 | addr&0xFFFF | 2 B |
| マスク書き | 0x40 | 0xBC | ((addr>>16)<<8)\|1 | `(addr&~3)&0xFFFF` | 8 B = value32 + mask32 |
| ブロック | 0x40 / 0xC0 | 0xBC | 同上 | 同上 | 64 B 単位、アドレスをチャンクごとに加算 |

マスク書きで addr が 4 バイト境界でない (addr%4==2) ときは、値をバイト 2-3、マスクをバイト 6-7 に置き、送るアドレスは `addr&~3`。
2 つ目の LSI は bRequest 0xBD (DT295 では使わない)。

## コマンド (doorbell 0xB8 / 0xB9) [確]

パラメーターを MB86M01 のメモリに 0xBC で書いてから、4 バイトのベンダー書き込み `{cmd, sub, par>>8, par}` (bmRequestType 0x40, wValue=0, wIndex=0) で doorbell を鳴らす。
bRequest 0xB8 = ch0 (System1 / メイン), 0xB9 = ch1 (System2 / I2C / B-CAS)。

| cmd | 用途 | ch | パラメーターのアドレス | 長さ |
|---|---|---|---|---|
| 1 | アイドルへの遷移 (-> 0x11) | 0 | | |
| 2 | 状態の遷移 (sub0 -> 0x10、sub1 -> 0x12 サスペンド) | 0 | | |
| 3 | 0xFFFF からの回復 (-> 0x10) | 0 | | |
| 4 | ストリームの準備 (ch0: sub0 = trc のホットロードの前, sub0x20 = System1 の準備 -> 状態 1。ch1: sub0x10 = System2 の準備) | 0/1 | | |
| 5 | ストリームの制御 (par = 2 開始 -> 状態 2 / 4 停止の前段 / 1 停止。sub1 はルートのスロットの書き換え) | 0/1 | 0x081000 (sub1 のみ) | 6 |
| 8 | type-8 メッセージ (認証、セキュアセッション、sysinfo) | 0 | 0x083000 | 512 |
| 9 | I2C | 1 | 0x0800C0 | 64 |
| 10 | B-CAS | 1 | 0x08219C | 272 |
| 11 | B-CAS | 1 | 0x081110 | 272 |

ACK (実機で確認): 割り込みステータス 0x090074 の bit3 (0x08) が ch0、bit1 (0x02) が ch1 の ACK。
ACK レジスター (ch0 = 0x080014、ch1 = 0x080016) は、上位バイトがコマンド種別のエコー、下位バイトが結果で、0x80 は拒否。
例: cmd1 -> 0x0100、認証 -> 0x0800、B-CAS -> 0x0A00、I2C (ch1) -> 0x0900、I2C を ch0 に送ると 0x0980 (拒否)。

0x090074 のほかのビット:

| ビット | 意味 |
|---|---|
| 0x0004 | 状態の変化 (状態は 0x082008) |
| 0x0100 | I2C の応答 (66 B @ 0x0823BE) |
| 0x0200 | B-CAS の状態の変化 (カードの抜き挿し)。274 B のメッセージ (0x0822AC) の先頭の 16 ビットの上位 4 ビットが状態 |
| 0x0400 | B-CAS の応答 (274 B) |
| 0x0800 | セキュアの応答 (512 B) |

- ステータスのクリアはプレーンな 16bit 書き込み `write16(0x090074, bit)`。
  マスク書きで W1C すると、同時に立った別のビット (I2C の応答 0x100 など) まで消える。
- 溜まったイベントのビットは放置しない。
  ストリーム中に処理していないビットが残ったまま次の doorbell を鳴らすと、ファームウェアが止まる (状態は 2 のまま TS が止まる)。
  doorbell の前に 0x090074 を読んで立っているビットを W1C し、EP 0x83 を読む、を空になるまで繰り返す。

ファームウェアの状態レジスター 0x082008: `0` = 未ロード, `0x10` = ブート済み (init が必要), `0x11` = アイドル (準備完了), `0x12` = サスペンド, `1` = System1 の準備済み (cmd(4,0x20) の後), `2` = ストリーム中, `4` = 停止処理中, `0xFFFF` = エラー。

- 0xFFFF からは cmd3 で 0x10 に復帰
- 0x11 では cmd3 と cmd(2,0) は拒否されるので、cmd(2,1) -> 0x12 -> cmd(2,0) -> 0x10 とする。
  ただしこの手順では前のセッションがファームウェアの中に残ったままで、それが切れるのが新しいセッションの途中だとファームウェアが止まる。
- 純正ドライバーは起動時に 0x11 を見つけると、idle ファームウェアをその場で再ロードする: cmd(4,0,1) (ACK のみ) -> イメージを EP 0x02 へ (trc のホットロードと同じ送り方) -> cmd(4,1,0) -> 0x10。
  それから認証する (本ドライバーも同じ)。
  純正は閉じるときにセッションを終える処理をしない (ストリームの停止は cmd(5,0,4), cmd(5,0,1), IDLE パラメーター, cmd(1,0,0) で、0x11 に戻すだけ)。

## ファームウェアのブート [確]

1. 0x90194[13:12]=1, 0x90198=0x40
2. 割り込みイネーブル (0x90078 / 0x901B4) を全ビット off
3. 割り込みを待ち (最大 100 ms)、0x90074 の bit2 を確認してクリア
4. idle ファームウェアを EP 0x02 に 64 KiB 単位で転送
5. 割り込みイネーブルを on、0x90070 の bit2=1 (開始)
6. 割り込みを待ち (最大 2 秒)、0x90074 の bit2 と、0x082008 が 0x10 か 0x11 であることを確認してクリア
7. 0x10 で version を検査 (reg 0x10、word3 の上位ニブル = 0)
8. 認証、IDLE パラメーター (0x080074 / 0x080078 へのマスク書き)、cmd1 -> 0x11
9. GPIO1 でチューナーをリセットし (low 20 ms -> high -> 5 ms)、B-CAS を初期化 (ch1 cmd 0x0A)。
   GPIO は 0x090014 が向き (1 で駆動)、0x090018 が値 (チップの 0xF10014 / 0xF10018) で、GPIO1 (bit 1) は復調とチューナーのリセット (負論理)

## 認証とセキュアセッション (type-8) [確]

type-8 の転送: パラメーターを 0x083000 (512 B) に書き、ch0 に doorbell `{8,0,0}`、ACK (0x0800) の後で応答を同じ 0x083000 から読む。
パラメーターのワード列は `[cmd,0,0,0,0,len_dwords,0xFFFF,0xFFFF, payload(BE dword)...]`。

起動時の認証: ファームウェアは認証を終えないと 0x10 -> 0x11 に進まない (cmd1 だけでは 0x10 のまま)。

1. MSG1 (内部 cmd 0x0101): 24 B の識別ヘッダー `{2018,5,1,1040,1,6}` (LE dword x6) を送り、チャレンジを受信
2. 応答を計算する: `idx = CMAC(K_auth1, blk1)[15] & 0xF` (blk1 = 定数 14 B + チャレンジ由来の 1 B + シード 1 B)。
   `response[0:16] = CMAC(K_auth2, keytable[idx][16:32] を最終ブロックに置いた 64 B)`、`response[16:20]` = 乱数。
3. MSG2 (内部 cmd 0x0102): 20 B の応答を送信
4. セッション鍵 SS = `CMAC(K_sess, {keytable[idx][28:32] + 定数 12 B} を最終ブロックに置いた 64 B)`

CMAC は標準の AES-128-CMAC (純正は CNG の CBC を IV を保ったまま呼んでいて、数学的に等価。NIST のベクターで確認)。
鍵と定数 (K_auth1/K_auth2/K_sess = `xmmword_1400784C8/D8/E8` XOR `_140078508/518/528`, 16x32 B の鍵テーブル 0x140077920, CMAC の定数ブロック) はドライバーのイメージから取り出し、`src/dt295/src/auth.rs` に置いてある。
同じ経路で sysinfo (cmd 0x0801) も応答する。

暗号化した RPC: 以下はすべて type-8 で、本体を SS で AES-128-CBC (IV = 0) で暗号化する。
ブロックは `[0]` group, `[1]` cmd, `[2]` sub, `[10..12]` 個数 (BE), `[12..]` 暗号化した本体。
応答も offset 12 から同じ方式。

| RPC | 内容 |
|---|---|
| CAS チャネル | `04/02/02` -> `05/02/06` x4 -> `06/0c/02`。純正はストリームの開始 (cmd(5,0,2)) の前に毎回送るが、送らなくても映像と音声は出る (地デジ, BS, WOWOW, CS, 全サービス。0x082028 を 0 にしても同じ)。本ドライバーは送らない (選局が約 90 ms 短縮) |
| リンク鍵 | `07/01/06`。要求の本体はノンス 4 B とセキュアのエンドポイントの番号 (System1 は 3、System2 は 0x1B) など。応答の本体を SS で復号した offset 4 の 16 B がリンク鍵 |
| keepalive (SECURE_REALTIME) | `02/01/02` のチャレンジに `02/02/04` で応答。最後の keepalive から約 60 秒でファームウェアが 0xFFFF になり、別のプロセスが認証し直しても延びない。認証のみでストリームを始めていないセッションは切れない。純正は認証の 30 秒後から 30 秒ごと (待機中もストリーム中も)。本ドライバーはセッションの最初の 1 回をストリームの開始時 (ストリームが無ければ認証の 5 秒後) に送り、その後は 12 秒ごと |

B-CAS カードのセッション: ch1 の cmd 0x0A で第 1 段 (`0a 00`) -> 第 2 段 (`0a 01`)。
ACK の下位が 0 なら受理 (0x0A00)、0x80 なら拒否 (0x0A80)。
カードが無くても受理される。

B-CAS の状態 (0x0822AC の先頭の 16 ビットの上位 4 ビット) [確: 読み方は純正と同じ / 推: 値の意味]:

| 値 | 観測した状況 |
|---|---|
| 0 | カードを抜いたとき、カードが無いときの第 2 段の後 |
| 1 | カードを挿したとき、カードがあるときの第 2 段の直後 |
| 2 | 挿し直したカードに、待機中に第 2 段のみを送った直後 (4 秒たっても 2 のまま。ストリームを始めると 3 になる) |
| 3 | 映っているストリームの開始から 3 秒後 |
| 5 | 接触が悪くて映らないストリームの開始から 3 秒後 |

純正は状態の通知 (割り込みの bit 9) を受けるスレッドで状態を記録し、第 2 段を送った後は、状態が 1 か 2 の間は待ち、0, 3, 4, 5 で待機を終える (4 は観測していない)。

## I2C (コマンド種別 9) [確]

- ch1 で送る (ch0 に送ると拒否)。
  エントリごとに、データがあれば 64 B のパラメーターブロックを 0x0800C0 に書いて doorbell -> ACK を待つ。
  データはバイト順のまま。
- 書き込み: `{9,0,slave,len}`。
  書き + 読み: `{9,2,slave,wlen}` (書きの部分) -> `{9,3,slave,rlen}` (読みの部分)。
- 最後のエントリの後、0x090074 の bit8 (0x100) で通知 -> 0x0823BE から 66 B を読む -> `write16(0x090074,0x100)`。
  応答の byte0, byte1 がステータス (両方 0 で成功), byte2 以降が読んだデータ。
  存在しないアドレスはステータスが 0 でない (スキャンで応答するのは 0x20 / 0x22 のみ)。

チューナーへは TC90522 のゲートウェイを通す (px4_drv の `tc90522.c` と同じ): 書きは復調のアドレスへ `[FE C0 reg data...]`、MxL 側の読みは `[FE C0 FB reg]` を書いてから `[FE C1]` で読む。
HORUS3A の読みはサブアドレスなし。

## フロントエンドの制御

選局には、第三者から提供された、純正の I2C 列を実測した列を使う (`src/dt295/src/fe1.rs`)。
起動時に T / S 両方の復調とチューナーを初期化し、S 側のチューナーを待機状態にする。

地デジ (ISDB-T):
- 毎回: S 側を待機状態にする -> T 側を復帰させる (`fe c0 0b 01`, `fe c0 12 01`, `03 00`) -> T 復調の前処理 -> チューナーの周波数 (reg 0x10 / 0x11) -> 開始。
  衛星の選局は T 側を待機状態にする (チューナー `0x12 = 0`、`0x0B = 0`、復調 `0x03 = 0x90`) ので、復帰させないとそれ以降の地デジが一切ロックしない。
- 周波数: reg 0x10 / 0x11 = `f[MHz] * 64` の下位 / 上位バイト (例: 557.142857 MHz -> 0x49 / 0x8B), reg 0x0F = 0x20 (6 MHz 幅)。
  純正ドライバーの MxL603 の SetFreq と同じで、受け付けるのは 90-770 MHz。
  チャンネルの中心周波数は奇数 MHz + 1/7 なので、下位バイトは 0x49 か 0xC9 になる。
  その後の reg 0x31 / 0x7C は、700 MHz 未満が 0x81 / 0x1F, 700 MHz 以上 (UHF 51ch から) が 0x91 / 0x9F (純正で唯一の、周波数による分岐)。
  CATV や VHF の周波数でも同じ書き方で、復調側の設定も周波数によらない (純正ドライバーと CoreSDK.dll の静的解析。CATV は実機では確認していない)。
- ロック: 復調 reg 0x80 の bit 2 以外が 0 (0x00 か 0x04)。
  電波の無いチャンネルは 0.2 秒ほどで 0xAF になり (bit 7 が立つ)、そのまま変わらない。
  電波のあるチャンネルでは bit 7 は立たず、0x2F -> 0x2E / 0x0E -> 0x06 -> 0x04 か 0x02 -> 0x00 と進む (bit 2 と bit 1 の消える順は決まっていない)。
  0x0E から 0x06 を経ずに 0x04 になることもある。
  0x04 になるのは選局から 0.6 秒ほど。
  bit 2 は、局や時間帯によって立ったまま消えないことがある (意味は分かっていない)。
  その状態でも TS は欠けずに出力されるので、bit 2 は判定に使わない。
  bit 1 は判定に使う (0x02 のまま止まる局は、まだ確認されていない)。
  他のドライバー: m-tsudo の PT3 は bit 3 のみ (bit 7 で打ち切る)、px4_drv は bit 5 と bit 3 に加えて reg 0xB0 の下位ニブルが 8 以上かを見る。
  Linux の tc90522 は bit 7-1 がすべて 0 であること (bit 2 も含む) を求めるが、その前に reg 0x96 の bit 7-5 のどれかが立っていればロックとする。
  ロックの後で復調の 0x1D / 0x1E / 0x1F = 0x02 / 0x2A / 0x8A を書く (純正と同じ)。
  これを書くまで、復調は TS を出力しない。
  待ちの間にロックしなかったとき (電波はある) も、待ちの終わりに書く。
  後からロックしたときに TS を出力するためで、ロックの前に書いてもロックまでの進み方と時間は変わらない。
  空きチャンネルには書かない。
  待ちの間にロックしたときは、書いた後もロックが続いているかを読み、外れていたら戻るのを最大約 1 秒待つ。
  reg 0x96 は空きチャンネルでも変動するので、判定に使えない。

衛星 (ISDB-S):
- 純正の選局列 (BS-15 の TS1 のキャプチャ) をそのまま流し、5 か所のみ差し替える: 周波数 `FE C0 00` (チューナーの reg 0x00-0x04), 帯域 `FE C0 09` = 周波数で選ぶ値, 復調 reg 0x8F / 0x90 = 放送の TSID の上位 / 下位 (Linux の `tc90522s_set_tsid` と同じ), チューナーの reg 0x50。
  周波数は純正ドライバーと同じ書き方で、IF を MHz に丸め、1100 MHz 以下は分周 4 (reg 0x04 = 0x80, 値は MHz の 2 倍)、それより上は分周 2 (reg 0x04 = 0x00, 値は MHz) とし、reg 0x00-0x01 にその値の 2 倍を BE で書く (reg 0x02 / 0x03 は 0。BS-1 の 1049.48 MHz は `10 64 00 00 80`, BS-15 の 1318 MHz は `0A 4C 00 00 00`)。
  Linux の `horus3a.c` も同じ式だが、分周 4 にするのは 1155 MHz 以下 (BS-5 の 1126.20 MHz も分周 4 になる)。
  帯域は HORUS3A の G_CTL (bit 7-5) と F_CTL (bit 4-0) で、Linux の `horus3a.c` と同じ表を使う (MHz に丸めて選ぶ。BS-15 の 1318 MHz は 0x8C, CS の 1600-1800 MHz は 0x44, 1800-2000 MHz は 0x22, 2000 MHz 以上は 0x00)。
  reg 0x50 は、チューナーから読む 2 B (サブアドレスなし) の 2 B 目の bit 6-5 が両方 1 なら 0xF1、そうでなければ 0xF0 で、書いた後に 40 ms 待つ (純正と同じ)。
  PLL 関係のチューナーの書き込みの後は約 80 ms 待たないと、0xC3 がロックにならない。
- BS の TSID は、上位 4 bit が 0x4, bit 11-9 が再編の回数, bit 8-4 がトランスポンダーの番号, bit 3-0 が相対 TS (例 0x4631 = BS-3 の TS1)。
  CS110 は 0x6xxx / 0x7xxx。
  4K (ISDB-S3) のトランスポンダーは受信できない。
- S 復調 reg 0x8E の bit 1 はダミーのスロットを落とす。
  0 だと CS のトランスポンダーは約 6.5 MB/s でヌルパケットが 3 割を超え、1 だと約 4.9 MB/s (第三者が実機で確認)。
  純正の初期化の値 0x26 は bit 1 が立っている
- ロック: 復調 reg 0xC3 の bit 7-4 がすべて 0。
  Linux の tc90522 は bit 7 を入力レベル、bit 6-5 をキャリア、bit 4 をロックとして見て、reg 0xC5 の bit 1-0 も見る (px4_drv は bit 4 のみ)。
  bit 3-0 はロックのビットではなく、PT3 のドライバーは bit 2 を TMCC の緊急警報、bit 1 を拡張のフラグとして読む。
- TS の一覧と選んだ TS: 復調 reg 0xCE から 16 B で、そのトランスポンダーの TSID が 8 個 (BE。0 と 0xFFFF は空き。TMCC 由来。BS-1 なら 0x4010, 0x4011, 0x4012)。
  reg 0xE6 の 2 B は流している TSID。
  トランスポンダーに無い TSID を書くと、先頭の TS を流して 0xE6 もその TSID になる。
  TSID を書かない (0xFFFF) と、先頭の TS を流すが 0xE6 は 0xFFFF のまま。

状態と C/N: T はロック 0x80, C/N は 0x8B の 3 B。
S はロック 0xC3, C/N は 0xBC の 2 B, 誤りカウンター 0xEB / 0xF0 (各 3 B。純正もストリーム中にこの 4 つを読む。正確な意味は分かっていない)。
C/N の dB への換算は、Linux の `tc90522.c` と同じ多項式:
- T: `P = 10*log10(5505024 / raw)`、`C/N[mdB] = 0.024*P^4 - 1.6*P^3 + 39.8*P^2 + 549.1*P + 3096.5`
- S: `P = sqrt(raw - 3000) / 64`、`C/N[mdB] = -1634.6*P^5 + 14341*P^4 - 50259*P^3 + 88977*P^2 - 89565*P + 58857`

## TS ストリーム (System1 / EP 0x81) [確]

純正の手順 (純正ドライバー + StationTV X の地デジの視聴を USB ETW で観測。アドレスと順序だけで、データの本体は記録されない):

1. 停止中なら ch0 `cmd(5,0,4)` -> `cmd(5,0,1)` -> IDLE パラメーター -> `cmd1` (-> 0x11)
2. type-8 のやり取り (停止から `cmd(4,0,0)` までの間と、ストリームの開始の後にのみ現れる)
3. ch0 `cmd(4,0,0)` -> trc ファームウェア (`trc_m_h.bin`, 1,497,200 B) を EP 0x02 に 64 KiB 単位で送信 (状態は 0x11 のまま)
4. ファームウェアのバージョンの読み出し (reg 0x10、8 B)
5. 0x1000-0x1AFF (2,816 B) をゼロにしてから、デコーダー窓を初期化 (0x1000-0x1FFF へのブロック書きとマスク書き)
6. `write16(0x082028, 0xFFFF)` (SYSTEMINFOMASKINIT) -> ch0 `cmd(4,0x20,0)` (-> 状態 1)
7. ch0 `cmd(5,0,2)` (-> 状態 2)。
   その ACK の後で EP 0x81 にバルク IN を投入する (投入の順序は結果に影響しない)。

本ドライバーの開始手順 (`src/dt295/src/s1/`):

1. 認証ごとに一度、ストリームの開始の前 (0x11 のとき) に、B-CAS カードのセッションの第 2 段とリンク鍵 (`07/01/06`)
2. `cmd(4,0,0)` -> trc ファームウェアのホットロード -> デコーダー窓の初期化 (純正の 721 回の書き込みをキャプチャから再生する。`decoder_init.{rs,bin}`) -> single-service (AUTO_PID on, PROGRAM_NUMBER = サービス ID), full-mux, または全サービス (AUTO_PID off、PROGRAM_NUMBER 0、ルートのスロットを明示的に書く。下の "ルートのスロット" セクション)
3. 0x082028 = 0xFFFF -> `cmd(4,0x20,0)` -> 状態 1 -> `cmd(5,0,2)` -> 状態 2。
   CAS チャネルは送らない (上の "認証とセキュアセッション" セクションの表)。
4. worker が EP 0x81 を読み、リンク暗号を解き、12 秒ごとに keepalive を送信
5. 停止は 2 -> `cmd(5,0,4)` (EP 0x81 を読み捨てて停止を完了させる) -> `cmd(5,0,1)` -> アイドル

カードのセッションによるゲート: `cmd(5,0,2)` の後で本編の ES を出力するかどうかは、ファームウェアが内蔵カードのセッションの状態 (ハードウェアの CAS ステータス由来のフラグ) で決める。
第 2 段を送っていないと、`cmd(5,0,2)` で 0xFFFF になる。
第 2 段を送ってもカードが無い (または正常に認識されていない) と、ストリームは動くが映像と音声が出ない (PAT、PMT、字幕などは出る)。
ストリーム中にカードを抜いても同じで、ファームウェアは止まらず、挿し直しても自動ではセッションを張り直さない。
起動からやり直すと復帰し、ストリームを止めて待機中 (0x11) に第 2 段だけを送り直しても復帰する (状態はすぐ 2 になり、ストリームを始めると 3 になる)。
生のスクランブルされた TS を取り出す経路は無い。
出てくるのはカードで復号済みの TS (デスクランブルを切れば、無料放送 + PSI + データ)。

リンク暗号: EP 0x81 の TS は payload だけが AES-128 で暗号化されている。
transport_scrambling_control = 01 のパケットが対象で、payload (アダプテーションフィールドの後ろ) の 16 B 単位の部分を CBC、端数を CFB に似た方式 (最後の暗号ブロックを暗号化して XOR) で復号する。
IV は固定の値、鍵は上のリンク鍵。
デバイスは最初に渡した鍵で暗号化し続け、セキュアセッションが切れて 0xFFFF になるまで新しい鍵を使わない。
その内側はなお ARIB の MULTI2 で、内蔵カードが解く。
パケットは 188 B、USB へは 64 KiB 単位で出てくる。

### ルートのスロット

デバイスが EP 0x81 に出力するのは、PAT と、デコーダー窓のルートのスロットに登録された PID だけ。
single-service (AUTO_PID on) では、PROGRAM_NUMBER の番組の PID をファームウェアが自分でスロットに入れる。
AUTO_PID off なら、スロットに書いた PID がそのまま出力される。

| アドレス | 内容 |
|---|---|
| 0x101A bit 15 | AUTO_PID_MODE。bit 12 は PAYLOAD_UNIT_START_DISABLE_MODE: 0 (純正の初期化の値) だと、一般のスロットは payload の無いパケット (PCR だけのパケット) を通さない。PMT と ES はどちらでも通る |
| 0x1018 | PROGRAM_NUMBER (AUTO_PID off なら 0 でよい) |
| 0x101C | 番組の映像と音声の stream_type (上位と下位のバイト。AUTO_PID off なら 0 でよい) |
| 0x101E-0x1024 | スロット 0-3 (専用: 映像, 音声, PMT, PCR)。AUTO_PID off では使わなくてよい |
| (なし) | スロット 4 は PAT。書かなくても出る |
| 0x1028-0x109C | スロット 5-63 (一般)。1 語 1 スロットで、`0x8000 \| PID` (bit 15 が有効) |
| 0x10A2-0x10E0 | スロットごとに、そのスロットをデスクランブルする ECM のスロット番号 (7 bit)。1 語に 2 スロットで、偶数のスロットが上位バイト。ECM のスロットは自分の番号を書く。0 はデスクランブルしない |
| 0x081000 | ストリーム中のスロットの書き換え: `{スロット << 8 \| ECM のスロット, 0x8000 \| PID, PID}` (BE の 3 語) を書いて `cmd(5,1,0)`。ACK (0x80014) の下位バイトが 0 なら受理。1 回約 2 ms |

- `cmd(4,0x20,0)` の前 (状態 0x11) にレジスターを直接書くのも、ストリーム中 (状態 2) にメールボックスで書き換えるのも有効。
  書き換えたスロットの前の PID は止まり、新しい PID が出る。
- 純正の初期化 (キャプチャ) はスロット 5-14 に SI (0x10, 0x11, 0x12, 0x14, 0x23, 0x24, 0x25, 0x28, 0x29) と NULL (0x1FFF) を入れ、PROGRAM_NUMBER は 43008。
- 複数の番組を同時に出せる: TOKYO MX (20ch) の MX1 と MX2 (別の番組, 映像と音声は別の PID, ECM は同じ 0x0031) を同時に出して、どちらもデスクランブルされる。
  地デジ (27ch の 4 番組), BS (BS-15 の 6 番組, BS-1 の 3 番組) でも全番組の PMT が出る。
  ECM の違う番組も同時にデスクランブルされる (CS110 の ND06 で 8 つの ECM の 8 番組)。
  地デジと BS は、1 つの TS の ECM が 1 つだった。
  ECM が 1 つなら、スロットを 59 個すべて使っても問題は無い (TOKYO MX)。
- 一度に追加する ECM が多いほど、ルートを書き終えてから 1-3 秒でファームウェアがコマンドに応答しなくなる (状態 0xffff。その前にスロットの書き換えが 0x0580 で拒否されることもある)。
  間隔をあけて追加すると止まりにくく、全部を遅らせてから一度に追加しても効果は無い。
  ストリームが流れ始めた後は止まらず、止まっても起動し直せば復帰する。
- PCR: 一般のスロットに入れた PCR の PID は、bit 12 が 0 だとパケットが 1 つも出ず (PCR だけのパケットは payload が無い)、1 にすると出る。
  専用のスロット 3 に入れると bit 12 が 0 でも出るが、同じ PID を一般のスロットにも書くと止まった。
  PCR が無いと、ffmpeg はデコードできても TVTest は映像も音も出さない。
- NULL をスロットに入れないと NULL パケットは出ず、USB のデータ量はおよそ半分になる (single-service の出力には入っている)。
  ただし SI のみのときはデータが少なく、USB へは 64 KiB 単位でしか出てこないので、最初の PAT まで 4.4 秒かかった。
  そのため NULL はスロットに入れたままにし、ホストが受け取ったあとで捨てる (System2 の TS の NULL も同じ)。

## TS ストリーム (System2 / EP 0x86) [確]

2 チューナーの機種 (PIX-DT295W、PIX-DT195W) の 2 つ目のチューナーが使う。
手順は純正の Mac 用ドライバーと同じ:

1. INIT_S2 (0x1B02-0x1B18 のビット欄): 入力のパケット長 0, 入力のクロックの極性 0, ACCUMULATION_MODE_OUT_S2 0, 出力のパケット長 1, DMA_SEL_OUT_S2 1, SCRAMBLE_MODE_S2 1 (System1 の 0x100E と同じ), CA_TYPE_S2 0, PROGRAM_NUMBER_S2 (地デジは 0 でも解除される)
2. ch1 `cmd(4,0x10,0)`
3. `07/01/06` でセキュアのエンドポイント 0x1B のリンク鍵を得る。
   これを送らないと、次の `cmd(5,0,2)` でファームウェアが 0xFFFF になる。
4. EP 0x86 にバルク IN を投入し、0x081100 = 0xFF00 -> ch1 `cmd(5,0,2)` -> 0x081100 = 0
5. 停止は ch1 `cmd(5,0,1)` の後に `07/03/04` (本体 `{0x1B, 1}`) でエンドポイントを解放

- trc ファームウェアは使わない。
  System1 と独立に開始・停止でき、どちらかのみでも両方でも動く。
- EP 0x86 は 192 B 単位 (4 B の後に 188 B のパケット)。
  パケットは EP 0x81 と同じ方式でリンク暗号化されていて、鍵はエンドポイント 0x1B のもの。
- カードで解除済みの、TS の全サービスが出る。
  開始から 0.3 秒ほどは、最初の ECM を処理するまでの分がスクランブルされたまま出る (本ドライバーは除く)。
- System2 の状態は 0x081104 (動作中は 0x0008)。
  0x082008 は System1 の状態で、System2 だけが動いている間は 0x11 のまま。
- カードのセッション (B-CAS の第 2 段) は System1 と共通で、起動ごとに 1 回
- 同じセッションで止めて開始し直すと、新しく得た鍵で復号できる (System1 の鍵のように最初の鍵を使い続けることはない)
- Windows の純正ドライバーの手順 (0x1B00 から 1280 B をゼロ, SCRAMBLE_MODE_S2 2, 0x081100 = 0xFFFF, エンドポイントの鍵の要求なし) では `cmd(5,0,2)` で 0xFFFF になる

## raw-TS 経路で使うブロック [確]

純正ファームウェアを使わない raw-TS 経路 ([raw-ts.md](raw-ts.md)) が、ホストから 0xBC で直接触るブロック。
cold の個体では純正の boot0 が動いていて、ピンの多重化と TS のエンドポイントは boot0 が設定済み。
下の書き込みは、どれも第三者が実機の cold から 1 つずつ外して必要と確認したもの (2 つ目の取り込み、TS の端子、ユニットの出力の経路の行は、PIX-DT195W の実機で、ビットを 1 つずつ cold の値に戻して必要と確認したもの)。
純正の立ち上げはほかにも多く書く (外部メモリの 0xFD0090, 0xF10080-0xF10098, ピンの多重化の 0xF1011C, 0xF001F0, 0xF1001C, 復調のサブブロック 0x16000xx, エンドポイントの初期化, 0x3002FFFF のリセットなど) が、外しても変わらない。

| ブロック | レジスター | 内容 |
|---|---|---|
| I2C コントローラー | 0xFD8FE0 (+0x00 状態, +0x04 制御, +0x08 分周, +0x10 データ) | 0xFD8010 の bit 4 (クロック) を立て、0xFD8014 の bit 4 (リセット) と 0xFD80C0 の bit 1-0 (起動時は 3。どちらかが 1 だとブロックが止まったまま) を落としてから、分周 0x3C と制御 0x42 を書く。チューナーの経路は上の "I2C (コマンド種別 9)" セクションと同じ |
| I2C のピン | 0xF10114 の bit 21-20 = 10 | 無いと誰も ACK しない |
| フロントエンドのリセット | 0xF10018 / 0xF10014 の bit 1 | GPIO1 (上の "ファームウェアのブート" セクション)。値を 1 にしてから駆動する |
| ユニットのゲート | 0xF10118 = 0xFFFF (16 bit) | cold の値 (0x9000) のままだと、2 つの取り込みブロックがどちらも 0 を返して書き込みを捨てる。開いたまま書いても、動いている取り込みは止まらない |
| 取り込みブロック | 0x1900000-0x1902FFF | 24 bit を超えるのでバンク窓を通す (下) |
| TS のエンドポイント | 0xFDBD84 (FIFO), 0xFDBD0C (bit 2 = 空き) | 512 B のバーストを FIFO に書き、0xFD814C = 8 -> 0xFDBD0C = 4 -> 0xFD814C = 0xF で確定。0xFD814C はバイトイネーブル (bit 0 が最上位のバイト, 既定 0xF) |
| 2 つ目の取り込み | 0x00D21000 (入力), 0x00D22000 (エンジン) | 1 つ目と同じ形で、24 bit の窓の中にある (バンク窓は要らない)。0x00D00000 の bit 7 (リセット。cold は 0xF0021F9F) を落とし、0x00D00004 の bit 10 と 13 (入力とエンジンのクロック。cold は 0x01000000) を立てる。どちらの語もほかのユニットと共有なので、このビットのみ変える |
| TS の端子 | 0xF1012C の bit 6 (16 bit) | 立てると 2 つ目の取り込みの入力に復調の出力 B が入る (無いと 1 つ目と同じ出力 A が入る)。1 つ目の取り込みは変わらない。PIX-DT195W の cold は 0x3830 |
| 2 つ目の TS のエンドポイント | 0xFDBD98 (FIFO), 0xFDBD34 (bit 2 = 空き) | EP 0x86。端点 n の状態は 0xFDBD0C + 8 × (n - 1)、FIFO は 0xFDBD80 + 4 × n。確定の手順は EP 0x81 と同じ |
| ユニットの出力の経路 | ユニット 0x016 (0x01600000) と 0x018 (0x01800000)。+0x0 リセット (bit 17 がコア), +0x4 クロック, +0x000A0000 から RAM | 読み出し器 2 (+0x1018 基点, +0x1028 大きさ, +0x1048 開始, +0x1038 終わり, +0x1078 長さ, +0x1068 = 0x01000000 で開始、bit 25-24 が動作中) がバッファの領域 2 へ読み、エンジン (+0x2004 = 長さ - 1, +0x2000 = 0x0D000041、bit 2-0 が動作中) が読み出し位置 (+0x10068) から出力ブロックへ送る。バッファ管理部 (+0x10030-0x100B4) は 16 bit で、語の上位の半分。出力ブロックは +0x5000 = 0x011080C0, +0x5008 = 0x11000000, +0x5004 = 0x01000000 で動く |
| ストリームのチャネル | 0xFD8200 + 0x20 × k (+0 制御, +4 設定, +8 状態) | ユニット 0x016 の出力はチャネル 0、0x018 はチャネル 2 へ入る。0xFD8010 の bit 16 + k (クロック) を立て、0xFD8014 の bit 16 + k (リセット) を 1 度入れて落としてから、設定 0xB09F0000 \| FIFO の番号 × 0x1000 と制御 2 を書く。FIFO の番号は EP 0x81 が 0、EP 0x86 が 4 |
| EP の DMA モード | 0xFDBD08 + 8 × (n - 1) (制御), 0xFDBC14 | 制御に 1 を書いて bit 0 が落ちるのを待ち、0x00FF6000 を書く (どちらも 0xFD814C でバイトを選ぶ)。0xFDBC14 の bit 16 + n を立て、bit n を落とす。CPU のモードに戻すときは bit 16 + n を落として bit n を立て、制御に同じ手順でもう一度 1 と 0x00FF6000 を書く |
| 出力の経路を開くビット | 0xF1010C の bit 15, 0xF10130 の bit 0, 0xF10128 の bit 11 (16 bit) | bit 15 が無いと出力ブロックがチャネルへ出さない。0xF10130 の bit 0 が無いとチャネルに 8 バイトのうち 1 バイトしか届かない。0xF10128 の bit 11 が無いと約 64 KiB で止まる。0xF1010C の bit 3 は立てない (USB 全体が止まる) |
| バンク窓 | 0xEA3D8 (書き), 0xE9EBC (読み) | boot0 の LDI:32 の即値にバンク (アドレスの上位) を書くと、0x80000 + (addr & 0x1FFFF) がその番地に届く。終わったら 0x00F00000 に戻す |

取り込みの手順 (選局してロックした後):

1. 0x1900404 の bit 18 を立てる (立たなければブロックが眠っている)
2. 0x1900000 = 0x00020000, 0x1900004 = 0x00001100。
   最初に書く (最後に書くと、電源投入後の最初の回はリングに何も届かない)
3. リング: 0x1902020 = 先頭 (物理アドレス), 0x1902024 = 長さ (64 の倍数のみ保持), 0x1902028 (書き込み位置。ハードウェアが進める) と 0x190202C (読み出し位置) を 0
4. 0x1901000 = 0x0607 (16 bit。入力の選択), 0x1901004 = 0x04000000 (無いと、電源投入後の最初の回は記録が 0x47 で始まらない)
5. 0x1901044 = 0x00BC0000 (0xBC = 188), 0x1901080 = 0x01000000, 0x1901040 = 0x03000000
6. 0x1902010 = 0x02000000 で開始

- 2 つ目の取り込みは、ユニットのゲートと 0x00D00404 の bit 18 (手順 1 の 0x1900404 と同じ形) の後に、リセットとクロックのビット、端子のビットを書き、同じ手順 (3-6) を 0x00D21000 / 0x00D22000 に行う。
  入力の選択は 0x0606 (純正の System2 の値。0x0607 でも入る)、リングは 0x02400000 からの 4 MiB。
  2 つの取り込みは同時に動く (PIX-DT195W の実機)
- 停止は 0x1902010 = 0x04000000 -> 0x1901040 = 0 -> 0x1902010 が 0 に戻るまで待つ。
  止めずに次の回を始めると連続性エラーが出て、0x1901040 を残すと次の回は流れの 6 割ほどしか届かない
- リングは 192 B の記録 (188 B の TS パケット + 4 B) の並び。
  SDRAM の 0x02000000 から 4 MiB を使える (CPU からは 0x82000000)
- 0xF10080-0xF100FF はホストから読まない (読むとチップが止まる)
- 0xF10120 (cold は 0x2800) の bit 2 を変えたところで、チップがリセットされて cold に戻った (raw-TS の立ち上げからやり直しになる)

## 純正ドライバーの通信の観測

- USBPcap では記録できない: `pxmb86m0x_usb.sys` は URB を `KSDEVICE->PhysicalDeviceObject` に直接 `IofCallDriver` するので、PDO の上にいる USBPcap のフィルターを通らない。
  本ドライバーの通信 (WinUSB) は USBPcap / usbmon で取れる。
- USB ETW (UCX / USBXHCI / USBHUB3) なら、すべての URB のセットアップパケットとバルクの長さが取れる (データの本体は記録されない)。
  `tools/usb_etw_capture.cmd [シリアル番号]` (管理者権限が必要。シリアル番号を付けると、記録を始めてから個体を再起動するので、純正ドライバーの起動から記録できる) で `temp\usbtrace.etl` に記録し、`tracerpt temp\usbtrace.etl -o usbtrace.xml -of XML -y` -> `dt295 etw-urbs usbtrace.xml log.tsv` でアクセスの一覧にする。
