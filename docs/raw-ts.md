# raw-TS 経路

スクランブルされたままの TS を配信し (ヌルパケットのみ捨てる)、B-CAS の解除をホスト側に任せる経路の、内部のまとめ。
解除先は、Windows (TVTest) では CAS プラグイン、Linux (mirakc) では録画のパイプラインに置いた外部ツール (libarib25 の `b25` など)。
使い方は、Windows が [usage.md](usage.md) の "`BonDriver_DT295.ini`" セクション (ini の `RawTS`)、Linux が同じく "`dt295 serve`" の "raw-TS モード" セクション (`/etc/dt295.conf` の `raw-ts`)。
どちらも個体を扱うのは `dt295 serve` で、Windows では BonDriver が起動したものが、ini の `RawTS` の要求 (`mode=raw-ts`) で個体を開く。
System1 (視聴) の経路は [development.md](development.md)、デバイスの仕様は [device.md](device.md)。

## 概要

- 通常の System1 経路がデバイスの中でデスクランブルまでするのに対し、raw-TS 経路はスクランブルされたままの TS をホストへ渡し、解除はホスト側に任せる
- どちらで動くかは、Windows は ini の `RawTS` (`1` で raw-TS, `0` 既定で System1)、Linux は `/etc/dt295.conf` の個体の `raw-ts` (`true` で raw-TS, 既定 `false` で System1)
- raw-TS モードは完全に自前コードのみ: レジデント (チップに常駐させる第三者のコード) も純正ファームも使わず (ユニットのコアと補助コアで動くのも自前のコードのみ)、ホストがチップを cold (電源投入直後) から起こし、ホスト面の I2C (`0x00FD8FE0`) で選局し、取り込みエンジンを 0xBC バンク窓で設定して、ユニットの出力の経路で EP へ送る (使えないときは自前の pump。下の "仕組み")
- 最初の選局だけ、cold の個体が要る (下の "最初のチューニングと再オープン" セクション)
- 2 チューナーの機種 (PIX-DT295W、PIX-DT195W) は 2 つのチューナーを同時に使える。
  1 つ目は復調の出力 A からチップの 1 つ目の取り込みと EP 0x81、2 つ目は出力 B から 2 つ目の取り込みと EP 0x86 を通る (下の "2 チューナーの機種" セクション)

## 機能差 (System1 との違い)

| 項目 | System1 | raw-TS |
|---|---|---|
| デスクランブル | デバイスの中 (内蔵スロットの B-CAS カード) | ホスト側 (Windows は TVTest の CAS プラグイン, Linux は b25 など) + PC/SC リーダーのカード |
| ホストへ出す TS | デスクランブル済み | スクランブルされたまま |
| ファームウェア | 純正のもの (idle と trc) | 要らない (ホストが cold から立ち上げる) |
| ベンダーコード | 動く (純正ファーム) | 一切動かない (レジデント, 純正ファーム不使用。ユニットのコアと補助コアも自前のコードのみ) |
| C/N | worker が毎秒読む実値 | worker が毎秒 ホスト面 I2C で読む実値 (System1 と約 1 dB 以内) |
| 最初の選局 | 速い | cold は立ち上げで遅い (Windows は open で prime, デーモンが開いている間は retune のみ) |
| B-CAS カードの抜き挿しからの復帰 | ドライバーの `CardWatch` | ホスト側の解除ツール任せ (カードがデバイス外のため) |

## 構成

raw-TS 経路のために、ハードウェアの土台を `dt295-core` に切り出し、自前のオンチップのコードとホスト側を `dt295-rawfw` にまとめた。

| crate | 種類 | 内容 |
|---|---|---|
| `src/dt295-core` | lib | ハードウェアの土台。レジスターとコマンドのプロトコル, I2C, フロントエンド (選局, ロック待ち, C/N), チャンネル表, ファームウェアの転送, 共有する型 (`System` / `Status` / `TsSink`) |
| `src/dt295-rawfw` | lib | 自前コードのみの raw-TS 経路。cold stream の worker, FR monitor のホスト側, ホスト面の demod I2C。`dt295-core` の上に乗る |
| `src/dt295` | lib | System1 の経路とアプリの土台。`dt295-core` と `dt295-rawfw` の公開 API を re-export する |
| `src/dt295-cli` | bin | `dt295 serve` が raw-TS 経路を呼ぶ (`serve/unit.rs` の `serve_raw`, 開始と最初の TS の待ちは `rawts.rs`) |
| `src/dt295-bondriver` | cdylib | `BonDriver_DT295.dll`。`dt295 serve` に `mode=raw-ts` で選局を頼み、open で prime する (`driver.rs`) |

ファームウェアの `.bin` はコミットしない ([development.md](development.md) の "方針" セクション)。

## 仕組み

### モードの選択

ini の `RawTS=1` で、BonDriver は `dt295 serve` への要求に `mode=raw-ts` を付ける。
`dt295 serve` は個体を開いたときの要求のモードで個体のスレッドを動かし、raw-TS なら選局は `serve_raw` (cold, 自前コードのみ) 経路へ回る。
最初の選局でチップを立ち上げ (`full`)、以降のチャンネル変更は board を立て直さず retune + 取り込み再 arm だけ (立ち上げ済みかはチップ上の monitor を読んで判断する `cold_monitor_installed`)。

経路はすべてホスト側で、cold の立ち上げはホストの 0xBC 書き込みとホスト面の I2C だけで通す。

### ストリームの開始

`dt295 serve` の `serve_raw` が `rawts::start` を呼ぶ。流れ:

1. 前の worker を止める。
   raw-TS 経路はデバイスが TS の全サービスを出し、サービスの選択とデスクランブルは TVTest (か録画のパイプライン) がするので、要求の `sid` は使わない。
2. チップに自前の monitor が載っているかを読んで、立ち上げ済みか判断する (`cold_monitor_installed`)。cold なら最初の選局で全部立ち上げ、立ち上げ済みなら retune と取り込み再 arm だけで速い。
   フラグではなくチップを読むので、worker の再起動や差し直し無しの再オープン (別のプロセスからも) をまたいでも正しく分かる (2 度目の立ち上げは fault するので、載っている monitor を読んで避ける)。
3. 新しい周波数で worker を起こし、TS が届くのを待つ (`rawts::wait_first_ts`)。
4. TS が流れたらクライアントに `ok` を返す。流れなければ worker を止め、理由 (`no lock` など) を返す。

成否は worker を持っているデバイスへ触らず、TS が届いたかで判断する (下の "worker とキュー" セクション)。

### worker とキュー

ストリーム中にデバイスと I/O するのは worker のみ、というのは System1 と同じ。
`Device::stream_start_cold` が worker を立て、worker が capture の TS を `dt295 serve` のキューへ積み、書き込みのスレッドがソケットへ書く。
worker はデバイスの I/O を操作 1 回ごとに取る (pump の呼び出し, I2C の転送 1 回, 取り込みの開始など。`dt295_rawfw::IoAccess`)。
worker は、CC を確かめたあと、ヌルパケット (PID 0x1FFF) を捨ててからキューへ積む。
地デジでは復調が出す TS の 4 割強がヌルパケットで、捨てないと約 30 Mbps になる (ほかのドライバーでは約 17 Mbps)。
BonDriver は受け取った TS を FIFO (`TsFifo`) に積み、`GetTsStream` は FIFO から読むだけ。
読み手が遅れてキューや FIFO があふれたら、捨てて数える ([fifo.rs](../src/dt295-bondriver/src/fifo.rs))。

### 立ち上げと取り込み

レジスターと値は [device.md](device.md) の "raw-TS 経路で使うブロック" セクション。

- 最初の選局: フロントエンドの立ち上げ (I2C コントローラー, I2C のピン, リセットの解除) -> 復調とチューナーの初期化 -> monitor の書き込み
- 選局ごと: 選局してロックを待ち、取り込みを設定して開始
- ストリームの終わり: 取り込みを止める。
  止まっていない (前の worker が異常終了したなど) ときは、次の設定の前に止める

### pump と取りこぼし

チップの capture ring は SDRAM の 0x02000000 からの 4 MiB で、CS の 1 トランスポンダー (約 4.9 MB/s) の約 0.85 秒分が入る。
ring を空けるのは、ふつうはユニットのフィーダー (下の "ユニットの出力の経路" セクション) で、チップの中で記録が書かれるたびに送る。
フィーダーが使えないときは、補助コアの先読み (下の "補助コアの先読み" セクション) と、worker が約 2 ms ごとに呼ぶ pump が空け、それ以上遅れると TS が失われ、ホストには CC の飛びとしてのみ見える。
純正ファームウェアの ring (192 KiB, CS で約 40 ms) では、地デジでも pump が遅れるとあふれる (地デジで 1 秒ごとに 600 ms 止めた試験で、192 KiB は CC の飛び 95 件と約 4 割の欠け、4 MiB は欠け無し)。
そのうえで worker は次のようにして pump を遅らせない。

- ロックしたら、worker のスレッドの優先度を上げる (`prio.rs`)。
  Linux は `SCHED_FIFO` の 1 で、nusb のイベントスレッドも上げる (拒否されたら nice -10)。
  非特権のプロセスは `RLIMIT_RTPRIO` と `RLIMIT_NICE` の範囲でのみ上げられる (systemd の `LimitRTPRIO=1` と `LimitNICE=-10`)。
  これは非力な機器のための設定なので、同梱の unit には書かない ([usage.md](usage.md) の "困ったとき" セクション)。
  Windows は `THREAD_PRIORITY_HIGHEST`。
- ストリーム中の C/N は、C/N のレジスターのみ読む (`cold_cn`)
- Linux (usbfs) は、EP の読み出しを 8 本のみ投げておく (停止時の取り消しの間、同じホストコントローラーの他の個体の制御転送が待たされるため)

worker は届いた TS の CC を PID ごとに確認し、pump を使うときはその間隔も測る。
ring が満ちる間隔 (約 0.85 秒) 以上はその場で WARN として出力し、欠けがあれば 10 秒ごとにも出力する。
欠けとみなすのは、その間隔があったときと、CC の飛びが壊れたパケット (復調器が直せなかったもの) の数を超えたときで、弱電界だけでは WARN にしない。
集計 (「raw-TS cold: streamed ...」) はストリームの終わりに必ず出力する。

### ユニットの出力の経路

チップのユニット 0x016 と 0x018 (純正ファームでは TS の多重化を動かす) は、それぞれ ring の読み出し器、バッファ、エンジン、出力ブロックを持ち、出力ブロックのパケットを USB のストリームのチャネルが EP の FIFO へ直接書く。
raw-TS では、ユニットのコアで自前のフィーダーを動かし、CPU が TS を写さずに ring から EP へ送る (`dt295-frmon` の `unit_feeder`、ホスト側は `dt295-rawfw` の `hwpath.rs`)。
1 本の経路で約 40 MB/s まで運ぶ (既知の模様を流した試験で、届いたバイト列は送ったものと一致)。

- 1 つ目の取り込みはユニット 0x016 とチャネル 0 で EP 0x81 へ、2 つ目の取り込みはユニット 0x018 とチャネル 2 で EP 0x86 へ送る。
  2 つの経路は別々で、互いの速さを分け合わない
- フィーダーは、取り込みが書いた記録 (192 B) を 1 つずつ、読み出し器 2 でユニットのバッファへ読み、エンジンで出力ブロックへ送り、取り込みの読み出し位置を進める
- 経路には、システムの 16 bit のレジスターの 3 つのビットが要る。
  0x00F1010C の bit 15 が無いと出力ブロックがチャネルへ出さず、0x00F10130 の bit 0 が無いとチャネルに 8 バイトのうち 1 バイトしか届かず、0x00F10128 の bit 11 が無いと約 64 KiB で流れが止まる
- 取り込みの設定と停止の前に、ホストはフィーダーを止めて応答を待ち、ユニットを止めて、EP を CPU のモードに戻す。
  フィーダーが動いていなくても、経路を始めた跡 (フィーダーの開始の語か、EP の DMA のモード) があれば、ユニットを止める (ストリームの途中でホストのプロセスが落ちると、フィーダーは満ちた EP を待って止まったままになる)。
  フィーダーが起動しないときは、EP を DMA のモードにする前に pump の経路に戻る (下の "補助コアの先読み" セクション)
- 経路を始める前に、前のストリームが EP に残したもの (ホストが読むのをやめたあとに送られた記録と、満ちていないパケット) を読み捨てる。
  満ちていないパケットは、pump の確定と同じ書き込みで送らせる
- ストリームの終わりには、フィーダーを止めて EP が静かになるまで読んでから、出しておいた読み出しを取り消す。
  Linux の EHCI では、EP がまだ送っている間に読み出しを取り消すと、ほかの個体のストリームのパケットがいくつか欠けた
- 0x00F1010C の bit 3 (USB ブロックを補助コアの側へ渡すビット。純正ファームは立てる) は立てない。
  立てると、補助コアで USB の処理が動いていないので、USB 全体が止まる

### 補助コアの先読み

ユニットの出力の経路が使えないときに、pump の経路で使う。

pump の時間は、SDRAM の ring の読み出し (1 語約 175 ns) と EP の FIFO への書き込み (1 語約 230 ns) でほぼ半分ずつ。
チップにはもう 1 つ FR のコア (補助コア、ユニット 0x017 のコア。純正ファームでは USB の処理を動かす) があり、raw-TS ではここで自前の先読みを動かして読み出しを肩代わりする (`dt295-frmon` の `aux_prefetch`、ホスト側は `dt295-rawfw` の `prefetch.rs`)。

- 補助コアは ring から 512 B ずつ自分の RAM (取り込みごとに 8 枠の 4 KiB) へ写し、取り込みの読み出し位置を進める。
  pump (`ts_pump_staged`) は写された枠を FIFO へ書くのみで、補助コアの RAM は SDRAM の数倍速く読める
- 補助コアは USB に触れない。
  補助コアから USB ブロックに届くのは 0x00F1010C の bit 3 で USB ブロックを渡したときだけで、その間はメインコアの EP0 が止まる
- 取り込みの設定と停止の前に、ホストはその取り込みを補助コアから取り戻し、応答を待つ (読み出し位置を 0 に戻す書き込みとぶつからないように)
- 補助コアが動かないときは、pump が ring から直接運ぶ
- RAM の語は、メインコアの書き込みが前後の語を少し前の値で書き戻すので、2 つのコアが書く語は 64 B ずつ離す

### 2 チューナーの機種

チップには同じ形の TS の取り込みが 2 つあり (0x0190xxxx と 0x00D2xxxx)、2 つ目の取り込みの入力には端子の設定で復調の出力 B が入る ([device.md](device.md) の "raw-TS 経路で使うブロック" セクション)。
1 つ目のチューナーは出力 A から 1 つ目の取り込み、2 つ目のチューナーは出力 B から 2 つ目の取り込みを通り、同時に流せる。

- 2 つ目のチューナーの worker は `Tuner2::stream_start_cold` が立てる。
  `Device` の worker と同じもの (`dt295/src/raw.rs`) で、取り込み, pump, EP はフロントエンドの出力で決まる (`fjcore::Capture`)
- どちらの worker も、デバイスの I/O を操作 1 回ごとに取る。
  立ち上げと取り込みの開始はそれぞれ取ったまま行い、選局は I2C の転送 1 回ごとに取る (`LockedBus`。間の待ちではロックを持たない)。
  片方の選局の間も、もう一方の pump は遅れない
- ユニットの出力の経路も pump も、取り込みごとに 1 つ (`hwpath.rs` の `path`、`dt295-frmon` の `PUMP_A` と `PUMP_B`)。
  2 つ目のリングは SDRAM の 0x02400000 からの 4 MiB
- cold の個体は、どちらかのチューナーの最初の選局で立ち上げる。
  立ち上げは I/O のロックを持ったまま行い、もう一方は立ち上げ済みかをチップ上の monitor で判断する
- `Device::set_tuner(1)` は、2 つ目のチューナーの TS を出力 A に出して 1 つ目の取り込みで受ける (`dt295 capture --raw-ts --tuner 2`)
- Windows の TVTest では、どちらの ini も `RawTS=1` にし、2 つ目のチューナーの ini に `TunerNumber=2` を書く (2 つの TVTest は同じ `dt295 serve` を通る)
- ユニットの出力の経路では、2 つのチューナーは別々のユニットとチャネルを通り、速さを分け合わない (1 本で約 40 MB/s)
- pump の経路では、2 つの pump はデバイスの I/O もチップの CPU も順に使うので、運べる速さを 2 つで分け合う。
  補助コアの先読みで 512 B が約 38 µs (先読みなしは約 54 µs) になり、2 つ合わせて ring の記録で約 11.9 MB/s まで運ぶ (先読みなしは約 9.4 MB/s で、TS は約 8.6 MB/s)。
  ホストによらない (Linux と Windows で同じ速さ)。
  先読みなしでは CS (約 4.9 MB/s) 2 本で両方が欠けた。
  先読みありでは CS 2 本も欠けない

### 自前のコードだけ

運用中も cold の立ち上げも、動くのはすべて自前のコード: boot0 の hook と body (`dt295-frmon` の monitor), ユニットのフィーダーと補助コアの先読み, ring から EP へ運ぶ pump, capture エンジンの設定 (ホストの 0xBC バンク窓), 復調の tune と retune (`fe1`)。
第三者提供のファームウェアも純正ファームも使わず、1 バイトも動かない。

### 開くときの prime (初回チャンネルの表示)

cold の初回 `SetChannel` は bootstrap で数秒かかり (地デジで約 2.5 秒)、その間 TS が出ない。
TVTest の viewer は初回チャンネルを描画し始められず黒いままになる (チャンネルを変えると直る)。
そこで BonDriver は `OpenTuner` で前もって datapath を bootstrap しておく (`prime_raw`)。
TVTest のスキャン (`.ch2`) の最初の地デジ局を `dt295 serve` に 1 度要求し、ストリームが始まったら止める (スキャンが無ければ何もしない)。
これで初回 `SetChannel` は速い retune になり、初回チャンネルがそのまま映る。
全体でかかる時間は変わらず、待ちが初回 `SetChannel` から open へ移るだけ。
cold の立ち上げは 1 プラグに 1 回で、prime で monitor が載った後は、選局のたびにチップを読んで立ち上げ済みと分かるので、立ち上げを繰り返さない。

### 開く時間

prime の立ち上げは resident の転送を伴わず、ホストの 0xBC 書き込みとホスト面の I2C だけでチップを cold から起こす。
cold の立ち上げは、フロントエンドの初期化 (約 1 秒) と選局を合わせて地デジで約 2.5 秒かかるが、prime でそれを open に移すので、初回 `SetChannel` は速い retune になる (上の "開くときの prime")。

### 最初のチューニングと再オープン

- 最初のチューニングは cold の個体が要る。
  cold からの立ち上げはホストの 0xBC 書き込みとホスト面の I2C だけで通す (ベンダーのコードは動かない)。
- そのあとは、TVTest を閉じて開き直すだけなら差し直しは要らない (その間に `dt295 serve` が終了して起動し直しても同じ)。
  monitor はチップに残るので、開き直してもチップを読めば立ち上げ済みと分かり、最初の選局は速い retune になる。
- USB を物理的に差し直すとチップが cold に戻る (RAM が消え、monitor も消える) ので、次の選局で改めて立ち上げる。
  差し直しは物理的な抜き挿し 1 回につき 1 度だけ。

### 止まったときの検出

worker は halt した状態でも fault しないので、TS が止まっても自分では気づけない。
`dt295 serve` のストリームのループが raw-TS 用に見張る:

- 最初の TS は最大 `RAW_FIRST_TS` (30 秒) 待つ。
  cold の bootstrap とロック待ち (衛星で最大約 8 秒) より短くすると、その途中で止めてしまい、チューニング前の EP の読み出しキューを壊してチューニングが失敗する。
- 流れ始めた後、`RAW_STALL` (8 秒) の間 1 バイトも届かなければ、データパスが止まったとみなして同じチャンネルを選局し直す (`raw_stall_due`)。
  worker が届けたバイト数が唯一の生存信号。
  ヌルパケットは捨てたあとなので数えず、ヌルパケットしか来ない TS も止まったとみなす
- worker が自分で終わっていたら (unplug など) 片付けて、デバイスが抜かれていればストリームを終えて閉じ、戻ってきたら開き直す (BonDriver は同じチャンネルを要求し直す)。

### C/N

worker はストリーム中に約 1 秒ごとに、復調の C/N をホスト面の I2C で読み (`cold_cn` が `fe1::read_cn` を呼ぶ)、デバイスの `Live` に publish する。
ストリームの開始時には、選局でロックしたときに読んだ値もすぐに publish する。
`dt295 serve` は選局の応答 (`ok cn=...`) と `status` の要求にその実値を返し、BonDriver の `GetSignalLevel` はそれを返す。
値が無ければ (流れ始める前など) 公称値の 30 dB。
System1 経路 (ファームウェア経由で読む) と約 1 dB 以内で一致する。

## Linux (mirakc)

Linux でも `dt295 serve` (デーモン) が raw-TS 経路を担い、`dt295 tune` のクライアントへ流す (`serve/raw.rs`)。

- 個体ごとに `/etc/dt295.conf` の `raw-ts = true` で有効化する
- cold の立ち上げは最初の選局で 1 回。
  デーモンが個体を開いたまま保持するので、以降のチャンネル変更は retune だけ (立ち上げ済みかはチップ上の monitor を読んで判断する)。
  物理的な抜き挿しで cold に戻る
- B-CAS の解除は mirakc のパイプラインで行う。
  チューナーを `decoded: false` にし、`filters.decode-filter` に外部ツール (libarib25 の `b25 /dev/stdin /dev/stdout` など) を置く。
  解除には PC/SC リーダーの契約済みカードと pcscd が要る
- 止まったときの検出は Windows と同じ `raw_stall_due` (最初の TS は最大 30 秒、流れ始めた後は 8 秒無信号で選局し直す)
- 2 チューナーの機種の 2 つ目のチューナーは、別のスレッド (`serve/tuner2.rs`) が `Tuner2` で受け持ち、1 つ目と同時に流す
- EPGStation からの録画と、ブラウザでの視聴まで、純正ファームを使わずに通ることを実機で確認している

## dt295 capture と dt295 logo

`dt295 capture --raw-ts` (と `RawTS=1` の ini、`raw-ts = true` の個体) も同じ経路で、1 回の取り込みごとにプロセスが個体を開いて閉じる。
`dt295 logo` も、`RawTS=1` の ini の個体ではこの経路で受信する。
開始, 最初の TS の待ち, TS が出なかった理由はデーモンと共通 (`rawts.rs`)。

- 立ち上げ済みかはチップ上の monitor で判断するので、別のプロセスからの 2 回目以降も retune だけ (最初の TS まで約 1.7 秒)
- 途中で強制終了 (TerminateProcess) されても、次のプロセスは retune で流し始める
- worker が自分で終わったときと 8 秒無信号のときは選局し直し、抜かれたときは終了する
- capture の worker は TS を queue に入れるだけで、ファイルやパイプへの書き出しは別のスレッド (チップのリングは 1 秒分ほどなので、書き出しを待つと TS が途切れる)
